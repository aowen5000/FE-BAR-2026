# BUILD: how FE-BAR-2026 was built

For what the system is and how to run it, see [README.md](README.md). This file covers how it was built.

## AI-assisted workflow

* **Who built it.** Every pipeline, notebook, SQL file, UC object, Lakebase object, model, agent and dashboard was built by **Genie Code** in workspace `fevm-workshop-guy`. Genie Code worked from prompts that alex.owen@databricks.com wrote with help from Claude. Those prompts are in `prompts/`.
* **Skills.** From Step 2 (gold) on, every session began by confirming access to the Genie Code skills installed by `/Workspace/Users/alex.owen@databricks.com/Install-Genie-Skills-Notebook/genie_code_agent_Skills_Install`. That notebook installs 31 skill folders under `~/.assistant/skills` (pipelines, Lakebase, git, dashboards, ML, agents and others). The relevant skill was loaded before each task.
* **Guardrails in the prompts.** If a permission or access error came up, Genie Code was to stop and flag it rather than work around it. Notebooks had to be committed with their outputs visible. Evidence had to be text only, with no screenshots.
* **Git.** Each step ran on its own branch in the Git folder `/Workspace/Users/alex.owen@databricks.com/FE-BAR-2026-repo` (remote `https://github.com/aowen5000/FE-BAR-2026`). Branches were merged into main with `--no-ff` (Step 1 used GitHub PR #1). The commit message carried the Genie conversation ID, the workspace and the date. Where that metadata was missing or wrong, it was corrected in a follow-up commit, not by rewriting history (`logs/commit_metadata_corrections.md`). Two author identities appear in history, both mine: `aowen5000@gmail.com` (Git folder integration and GitHub web UI) and `alex.owen@databricks.com` (git CLI); see "Commit identities" in README.md.

## Key decisions

| Decision | Reason | Evidence |
| --- | --- | --- |
| Synthetic data scale and seeded cohort | 10K customers, 5K merchants, 500K transactions and 50K prior cases (seed 42) is large enough for a time split and a rare (~2%) label, and small enough for fast serverless runs. Seeded cohorts (high-amount cross-border, new-device online, unusual spend, and a combination) carry elevated fraud rates over a ~0.5% baseline. This gives the model a signal to learn and the agent a signal to explain | `card_transaction_bronze_generator.ipynb` (Configuration, Validation cells); `prompts/step1_3458967129203277.md` |
| JSON bronze with 15% DQ error injection | Raw landing data should look realistic: duplicate rows, null `txn_id` and null `customer_id`. This lets silver expectations and dedup be tested. Bronze holds 537,505 transactions and silver keeps 1 row per txn_id | `card_transaction_bronze_generator.ipynb` (`DQ_ERROR_RATE = 0.15`); `logs/update_60f6d1de_full_refresh_2026-10-15.md` |
| SNAPSHOT sync, not Triggered | Triggered sync failed on both tables with `MATERIALIZED_VIEW_CDF_REQUIRES_EXTERNAL_METADATA`: CDF reads from an MV need the Beta external-metadata feature, and the pipeline channel was CURRENT. The gold MVs are fully recomputed on each refresh anyway, so a full snapshot is equivalent | `logs/lakebase_sync_2026-10-17.md` "Failed Triggered Sync Attempt", "Why SNAPSHOT" |
| Synced tables in the `fe_bar_lakebase` catalog, not in `fe_bar_a0` | The first (failed) attempt registered the synced tables in `workshop_guy_catalog.fe_bar_a0` (`synced_txn_features`, `synced_customer_risk_profile`). The final design maps database `fe_bar_db` to its own UC catalog `fe_bar_lakebase` (MANAGED_ONLINE_CATALOG) with schema `fraud`, so the Postgres layout (`fraud`, `fraud_gov`, `cases`, `fraud_dash`) is visible in UC unchanged. The sync pipeline's own storage stays in `workshop_guy_catalog.fe_bar_a0` | `logs/lakebase_sync_2026-10-17.md` "Infrastructure", "History"; `prompts/step3_3367633421784666.md` |
| LightGBM and a time split | The prompt preferred LightGBM. It handles the 3 categoricals natively, takes `scale_pos_weight` for the ~2.4% label (41.2584), and gives exact TreeSHAP through `pred_contrib`, which scoring uses for per-row top-3 signals. XGBoost was the allowed fallback and was not needed. The split is by time (cutoff 2026-09-21 15:20:18, 80/20) so the test set is later than training, as in production | `logs/ml_training_2026-10-20.md`; `logs/batch_scoring_2026-10-20.md` |
| Block and review thresholds | Block = lowest score where test precision >= 0.50 (0.950267). Review = highest score where cumulative test recall >= 0.60 (0.871416). Both are logged as MLflow params and read at scoring time, never hardcoded | `logs/ml_training_2026-10-20.md` "Thresholds"; `fraud_batch_scoring.ipynb` code cell 4 |
| Cohort lift and non-cohort PR-AUC check | The seeded cohort has a 9.70x fraud lift, but it is only 1.0% of the top 500 scores. PR-AUC on non-cohort rows is 0.2809, equal to overall, so the model learned signal beyond the seeded rule | `logs/ml_training_2026-10-20.md` "Seeded cohort lift" |
| Calibrated confidence instead of the 0.03 placeholder | The Step 5 rule ("high if 0.03 beyond the threshold") had no empirical basis. Confidence now comes from the observed test-set precision per score bucket in `risk_score_calibration`: high >= 0.70, medium >= 0.30, else low. TXN-0234209 moved from "high" to "medium (precision 0.50 in block_band, n=288)" | `logs/agent_governance_2026-10-21.md` Item 8; `validation_notebooks/fgac_hardening.ipynb` Item 8a |
| Agent tool design | UC functions cannot get a Lakebase OAuth credential or open a Postgres connection, so `create_fraud_case` was agent-side from the start. UC reads of `fe_bar_lakebase` run as a non-identity-aware reader role (and see 0 case rows because of RLS). So in the hardening pass all four tools moved to agent-side Python under `SET ROLE fraud_triage_agent`, with the same names and docstrings. Each tool returns `_implementation` and `_objects_read` for the trace. `create_fraud_case` is idempotent (partial unique index, existing open case returned). The system prompt requires the risk and signals tools before any claim, the model's action as default, and case creation only on request | `logs/agent_governance_2026-10-21.md`; `logs/fgac_hardening_2026-10-21.md` Item 5; `fraud_triage_agent.py`; `fraud_triage_agent.ipynb` E.1 to E.6 |
| Lakebase FGAC design | NOLOGIN roles `fraud_pii`, `fraud_analyst`, `fraud_lead`, `fraud_triage_agent`. Synced tables cannot take RLS (owned by the sync writer), so `fraud_gov` security_barrier views apply the row rule (amount > 10000) and column rule (`amt_to_monthly_spend`) via `pg_has_role(..., 'fraud_pii')`, and no role has a grant on `fraud.*`. `cases.*` uses ENABLE + FORCE RLS with per-role policies. `db_inserted_by DEFAULT session_user` is checked by the agent INSERT policies, so attribution cannot be spoofed by a free-text label. Alternative documented: SNAPSHOT-sync a pre-filtered UC view so restricted rows never reach Postgres. Not used, because it needs a second copy per persona and a dynamic per-user filter cannot work on a static copy | `lakebase_fgac.sql`, `lakebase_fgac_hardening.sql`, `logs/lakebase_fgac_2026-10-21.md`, `logs/agent_governance_2026-10-21.md` Items 4 and 7 |
| Dashboard reads from `fraud_dash` views | The UC path cannot tell viewers apart (`databricks_reader_17063`), so the dashboard shows only non-pii-safe data. `fraud_dash` views are owned by `fraud_lead`, whose existing RLS policy covers the case rows. They exclude high-amount txns and never select `notes`, `created_by` or `db_inserted_by`. They pre-aggregate so the dashboard never pulls 464K rows. No RLS policy was added for the reader role, because that would expose the raw `cases.fraud_cases` (including `notes`) through UC | `lakebase_dashboard.sql`, `logs/dashboard_2026-10-22.md` "UC Reader Role", "Deny Tests" |

## What I would do next (Exceeds tier)

* **Vector Search grounding** over `fact_prior_fraud_cases_silver` and case notes, so the agent cites similar past cases when explaining a flag.
* **Genie space over the gold tables** (`txn_features_gold`, `customer_risk_profile_gold`, `scored_transactions`) for the Head of Fraud Risk Ops to ask ad hoc questions, with UC row filter and mask enforced per user.
* **Real-time serving**: deploy the agent with its own service principal mapped to `fraud_triage_agent` (so `db_inserted_by` identifies it), and serve `fraud_risk_model` for online scoring of new transactions.
* **`mlflow.genai.evaluate`** on a labelled set of flagged transactions, with judges for groundedness (no invented scores), correct action, and no case creation during plain explanation.
* **Drift monitoring** on `txn_features_gold` and `scored_transactions` (feature drift, score distribution, block-band precision against later labels), feeding retraining and recalibration of `risk_score_calibration`.
