# Known limitations

Moved from README.md in Step 10. Each item was still true when checked on 2026-11-06. None of them is fixed in Step 10. 100% synthetic data.

## Added in Step 10 (checked 2026-11-06)

* **High-value flagged transactions cannot be triaged in Genie, the dashboard or the App.** The `fraud_dash` views drop amount > 10000 for everyone. In the full synthetic set the model flags 705 of the 751 transactions with amount > 10000 (block or review). 200 of them are fraud, worth $3,588,732.92, and 505 are false positives. 0 of them are visible through `fraud_dash`. Source: `validation_notebooks/business_value.ipynb` code cell 6 "B.4b High-value slice and headline KPIs in two scopes"; `logs/business_value_2026-11-06.md` "B.4b-1". Options (redact the amount instead of filtering rows, or a pii-only view schema) are in `logs/gold_governance_2026-11-04.md` "Still open".
* **`scored_transactions` has no row filter or mask of its own.** It is closed only by grants: `account users` has no privilege on it after the catalog grant narrowing. `information_schema.row_filters` for `fe_bar_a0` lists only `fact_transactions_silver` and `txn_features_gold`. Reason: Lakebase synced tables cannot read a source with a table-level row filter (`ROW_LEVEL_SECURITY_FEATURE_NOT_SUPPORTED.TIME_TRAVEL`, job run 273696236528085, `logs/gold_governance_2026-11-04.md` "Job / sync test").
* **`txn_features_gold.amt_to_monthly_spend` is unmasked.** It is closed only by grants. `information_schema.column_masks` for `fe_bar_a0` lists only `customer_risk_profile_gold.avg_amount_30d` and `dim_customer_silver.avg_monthly_spend`. Source: `logs/gold_governance_2026-11-04.md` "Still open".
* **Per-user on-behalf-of (OBO) authorization is not implemented in the App.** The app acts as one identity for every user: all Postgres writes, Genie questions and warehouse queries run as the app's service principal, so the audit trail shows the app, not the analyst who clicked. A search of `app/app.py` and `app/app.yaml` for OBO or user-token handling found none.
* **Genie space CAN_RUN is per user, not per group.** The permissions API on 2026-11-06 shows CAN_RUN for the app service principal and the non_pii test user (user ID 72697000497660). The `non_pii` group has none.

## Carried over

* Lakebase synced tables are owned by the sync pipeline's writer role, so they cannot carry Postgres RLS. UC row filters and masks are not propagated to them either. Governance is applied through the `fraud_gov` security_barrier views, and no governed role has a grant on `fraud.*`. A stricter alternative (sync a pre-filtered UC view) is documented in `logs/agent_governance_2026-10-21.md` Item 4.
* UC queries on `fe_bar_lakebase` run in Postgres as `databricks_reader_17063`, which is not identity-aware. Through UC, `fraud_gov` always returns the non-pii result and `cases.*` returns 0 rows. The dashboard therefore shows only non-pii-safe data, from `fraud_dash`.
* Membership in the `fraud_pii` Postgres role is managed manually. `pii_role_sync.py` only prints a plan (dry run by default).
* In the Databricks App the agent runs in-process as the app's service principal, which logs in to Postgres as its own role (`8f239f44-078a-4f8f-90f1-4c1b0bcdc26c`, member of `fraud_triage_agent` only). `db_inserted_by` therefore tells the app apart from a human: live-test case `5af3575c-cda8-47cb-97be-021b26dca000` has the app role, the 227 earlier cases have alex.owen (`logs/app_2026-11-04.md`). Notebook runs of the agent still connect as alex.owen.
* The approve-band guardrail ("an approve-band transaction must not be opened as block") is enforced in `create_fraud_case` since commit ea2ab2b (Step 9). Registered agent @champion v3 predates this and enforces it only through the system prompt; it has not been re-registered.
* The app's own stdout logs (`/logz`) need interactive OAuth and can't be read from a notebook, so request evidence for the app comes from the audit log and query history (`logs/app_requests_2026-11-04.md`).
* The app's warehouse CAN_USE comes through the workspace `users` group, not an explicit grant to its service principal.
* The agent is registered in UC (@champion v3) but not deployed. Its Lakebase dependency is not declared as an MLflow resource: `mlflow.models.resources.DatabricksLakebase` (MLflow 3.12) only accepts a provisioned `database_instance_name`, and the Lakebase Autoscaling project `fe-bar-fraud-analytics` has no database instance. A deployment would need Lakebase credentials provided another way, for example running as a service principal with its own Postgres role (`logs/evidence_pass_2026-11-01.md` section 12).
* The data is 100% synthetic, with an intentionally seeded fraud cohort. Metrics describe this synthetic set only. Scaled issuer numbers in `logs/business_value_2026-11-06.md` "B.4" are illustrative, not measured.
* Dashboard dataset latency (p95 up to 8.7 s) is serverless SQL through UC on compute that was not fully warm. It is not Lakebase point-read latency.
* The analyst minutes per case (15 to 20 manual, 2 to 3 with the agent) are assumptions from the original plan, not measurements. The measured agent run time is 19.9 s median over 9 traced runs (`logs/business_value_2026-11-06.md` "B.3b").
